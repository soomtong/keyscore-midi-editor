# 01 — 작업 프로토콜: 계획 → 구현 → 검증 → 적대적 리뷰

Task 하나를 처리하는 루프다. 에이전트는 이 루프를 벗어나지 않는다.

## 역할

세 역할을 둔다. 같은 모델이라도 역할마다 새 세션(또는 명시적 역할 전환)으로 돌린다. 구현자가 자기 코드를 리뷰하지 않는다.

| 역할 | 할 일 | 하지 않을 일 |
| --- | --- | --- |
| 계획자 | Task 범위 확정, 인터페이스 초안, 테스트 목록, 리스크 | 코드 작성 |
| 구현자 | 코드·테스트 작성, 자동 게이트 통과, 보고서 | 자기 리뷰, 범위 확장 |
| 적대적 리뷰어 | 깨뜨리기, 불변식 위반 찾기, 요구사항 불일치 찾기, 판정 | 직접 수정 |

## 루프

~~~
[1] 계획      templates/task-plan.md 작성 → docs/reports/<task>/plan.md
[2] 구현      브랜치 생성 → 테스트 먼저(실패 확인) → 구현 → 테스트 통과
[3] 자동 게이트  cargo fmt --check, clippy, test, deny, bench(해당 시)
[4] 보고      templates/task-report.md 작성 → docs/reports/<task>/report.md
[5] 적대적 리뷰  templates/adversarial-review.md → docs/reports/<task>/review-N.md
[6] 판정      병합 가능 / 수정 후 재리뷰 / 범위 재정의
[7] 수정      지적 사항마다 커밋 하나. 리뷰어가 쓴 깨뜨리는 테스트는 그대로 저장소에 남긴다
[8] 재리뷰    [5]로. 3회 재리뷰에도 판정이 안 나면 결정 요청으로 전환
[9] 병합      squash 금지. 리뷰 기록이 커밋 이력에 남아야 한다
~~~

## [1] 계획 단계 규칙

- 단계 파일의 Task 항목을 그대로 복사하지 않는다. 그 항목을 읽고 「무엇을 만들면 끝인가」를 자기 말로 다시 적는다. 다시 적은 것이 원문과 다르면 그 차이를 명시한다.
- 공개 인터페이스(타입·함수 시그니처)를 먼저 적는다. 구현자는 이 인터페이스를 바꿀 때 계획 파일도 고친다.
- 테스트 목록을 먼저 적는다. 「이 테스트들이 통과하면 Task가 끝난 것」이어야 한다. 게이트에 적힌 테스트는 반드시 포함한다.
- REQ와 어긋나거나 REQ에 없는 결정이 필요하면 `docs/decisions/<날짜>-<주제>.md`를 만들고 멈춘다.

## [2] 구현 단계 규칙

- 테스트를 먼저 쓰고 실패하는 것을 확인한 뒤 구현한다. 실패 확인 없이 통과한 테스트는 「테스트가 아무것도 검사하지 않는다」로 간주한다.
- Task 범위 밖의 코드를 건드리지 않는다. 필요하면 별도 Task를 제안한다.
- 하나의 커밋은 하나의 논리적 변경. 「WIP」 커밋을 남기지 않는다.
- 기존 테스트를 지우거나 `#[ignore]`하지 않는다. 바꿔야 하면 이유를 커밋 본문에 적는다.

## [3] 자동 게이트

모든 Task 공통:

~~~
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check
~~~

단계 파일이 추가 게이트를 지정하면 그것도 통과해야 한다(벤치 기준, 루프백 지연, 스냅샷 등).

## [5] 적대적 리뷰 규칙

리뷰어의 목표는 「승인」이 아니라 「깨뜨리기」다. 다음을 반드시 한다.

1. 테스트를 읽기 전에 코드를 읽고, 「내가 테스트라면 무엇을 검사하겠는가」를 적는다. 그 다음 실제 테스트와 비교해 빠진 것을 찾는다.
2. 깨뜨리는 테스트를 최소 하나 작성해 실행한다. 통과하면 「깨뜨리지 못함」을 기록하고, 실패하면 그 테스트를 PR에 추가한다.
3. 불변식(겹침 없음, 노트는 클립 안, 틱 ≥ 0, 채널 1–16 등)을 깨뜨리는 경로를 찾는다. 공개 API만으로 깨뜨릴 수 있으면 「차단」 판정.
4. REQ 요구사항 ID를 하나씩 대조한다. 구현이 요구사항을 「대략」 만족하는 곳을 찾는다. 「대략」은 불일치다.
5. 실시간 경로(스케줄러)에 할당·락이 들어왔는지 코드로 확인한다. 추측하지 않는다.
6. 에러 경로를 본다. `unwrap`·`expect`가 제품 코드에 있으면 각각 이유를 요구한다.
7. 판정은 세 가지뿐: 「병합 가능」「수정 후 재리뷰」「범위 재정의」. 「대체로 괜찮음」 같은 판정은 없다.

리뷰어가 하지 않을 것: 스타일 지적(fmt·clippy가 잡는다), 자기가 선호하는 설계로 바꾸라는 요구(REQ와 계획 파일이 기준), 직접 수정.

## 결정 요청

~~~
docs/decisions/2026-10-12-clip-overlap-on-paste.md

# 결정 요청: 붙여넣기 시 클립 겹침 처리
- 관련 REQ: 5.10, 7.5
- 상황: ...
- 선택지: A ..., B ..., C ...
- 구현자 추천: B, 이유 ...
- 결정: (사람이 적음)
~~~

결정이 적힐 때까지 그 Task는 「보류」. 의존하지 않는 다음 Task를 진행한다.

## 단계 출구 게이트

단계 파일 끝에 있는 출구 게이트는 그 단계의 모든 Task가 병합된 뒤 한 번 더 수행한다. 사람이 수동 항목을 확인하고 `docs/reports/stage-<n>-exit.md`에 서명한다. 서명 없이 다음 단계로 가지 않는다.
