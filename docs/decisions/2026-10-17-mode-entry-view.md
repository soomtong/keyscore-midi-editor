# 결정: 모드에 들어갈 때 뷰(배치 뷰·피아노롤)

- 날짜: 2026-10-17
- 상태: 결정됨(에이전트, REQ 문장 근거). 사람이 다르게 정하면 `crates/keyscore-app/src/mode.rs`의 `Mode::needs_piano_roll` 한 곳을 고친다.
- 관련: REQ 5.1, 5.5, 5.9, 5.10, 5.11, 5.15, S2-T3 리뷰 1 지적 1, 리뷰 2 지적 1, A13 결정(`2026-10-17-keymap-conflicts.md`)

## 상황

REQ는 배치 뷰에서 입력 모드로 들어갈 때 뷰를 어떻게 하는지 직접 적지 않는다.
- S2-T3 처음 구현은 「노트 입력 모드(Step, Sequence, Lyric)는 피아노롤로 옮긴다」였다. 그러자 배치 뷰에서 `Ctrl+Tab` 한 바퀴가 뷰와 선택을 바꿔 5.11 「현재 커서 위치를 유지한 채 모드만 바뀐다」와 어긋났다(리뷰 1).
- 그 규칙을 모두 빼자, 배치 뷰에서 `w`(Lyric)·`shift-c`(Controller)가 배치 뷰 그대로 들어가 5.15(「커서 위 노트부터」, 「피아노롤은 가사 입력 중인 노트를 강조」)와 5.9(Controller 모드는 피아노롤 아래 레인을 키운 화면)와 어긋났다(리뷰 2).

## 결정

- Step, Sequence, Play, AI: 모드만 바꾼다. 뷰·선택은 그대로다.
  - 근거: 5.11 모드 순환 문장. 5.10 「클립 밖에서 Step·Sequence 입력을 시작하면 마디 단위로 새 클립이 자동으로 생긴다」와 5.11 「목적지 시간에 클립이 없으면 배치 뷰 기준의 빈 자리에 커서를 두고, 입력을 시작하면 클립이 생긴다」는 배치 뷰 위치에서의 입력을 전제한다.
  - vim `i`도 같은 규칙을 따른다(`Ctrl+Tab`과 나란한 진입이라는 5.11 문장).
- Lyric, Controller: 피아노롤로 옮겨 들어간다(5.15, 5.9 문장). 뷰가 바뀌므로 선택은 비운다(배치 뷰의 클립 선택은 노트 선택이 아니다). 이 두 모드는 순환에 없어 5.11과 부딪히지 않는다.
- 나올 때(`Esc`)는 A13 결정대로 뷰를 바꾸지 않는다.

## 이월

- S3(Step 입력): 배치 뷰에서 Step에 들어갔을 때의 커서·클립 생성 표시를 실제로 그린다. 그때 이 결정이 화면에서 어색하면 다시 연다.
  - S3-T4c(2026-10-30, 에이전트 해석): 배치 뷰 Element(트랙×시간 격자)는 S4-T1이라, 지금 배치 뷰 자리표시 안에 글로 보인다. 첫 줄은 `Step: <트랙> <마디.박.틱>`, 둘째 줄은 커서가 든 클립(「클립 「이름」 안」, 이름 없으면 시작 위치), 클립 끝에 이어 쓰면 「… 끝에 이어 쓴다」, 클립 밖이면 「입력하면 마디 a–b에 새 클립」(지금 길이의 음 하나로 `clip_for_notes`와 같은 계산) 또는 쓸 수 없는 이유. 결정(뷰는 배치 뷰 그대로)은 바꾸지 않는다. 격자 위의 커서와 고스트 클립 블록은 S4-T1 이월이다.
- S6(가사·컨트롤러): 커서 위 노트가 없을 때의 Lyric 진입 동작.
