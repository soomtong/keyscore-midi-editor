# 결정 요청: 카운트 접두와 키가 아닌 실행 경로(메뉴·툴바·팔레트)

- 날짜: 2026-10-17
- 상태: 결정됨(C)
- 관련: REQ KM-5(카운트 접두는 vim 프리셋용으로 엔진이 지원), 5.7, 5.8.1, UI-2(팔레트), UI-11(메뉴), S2-T2 리뷰 3(판정 「범위 재정의」), 결정 요청 `2026-10-17-keymap-conflicts.md` A9(vim 숫자 키)
- 미룬 수용 테스트: `crates/keyscore-app/tests/deferred/count_non_key_paths.rs`

## 상황

vim 프리셋에서 `3 j`는 「세 번 아래로」다. KM-5는 엔진이 카운트를 지원한다고만 하고, 카운트를 친 뒤 키가 아닌 경로로 Action이 실행될 때를 정하지 않는다. 키가 아닌 경로는 메뉴 막대, 툴바 버튼, 팔레트다.

지금 구현(S2-T2)은 이렇다.
- 카운트는 키 입력으로 시작된 실행에만 붙는다. 메뉴·팔레트로 실행된 처리기는 카운트를 받지 않는다.
- 숫자도 대기 중인 시퀀스도 아닌 키 입력이 끝나면 카운트를 비운다.

GPUI는 「모든 Action 실행」을 지켜볼 훅을 주지 않는다. 그래서 남는 경우가 셋이다.
1. `3` → 메뉴로 실행 취소 → 한참 뒤 `j`: `j`가 3을 받는다. 메뉴 실행이 카운트를 비우지 못한다.
2. `3 g`(시퀀스 대기 중) → 메뉴로 실행 취소: 메뉴 처리기가 3을 받을 수 있다. 실행 취소가 세 번 된다.
3. `3 y`(대기 만료로 `y` 실행): `y`가 3을 받는다. 지금은 맞게 동작하고, 1·2와 같은 표시를 쓰므로 함께 정해야 한다.

## 선택지

- A. 지금 의미를 유지하고, 1·2를 한계로 문서화한다. 메뉴·팔레트는 마우스·팔레트 조작이라 카운트를 친 직후 쓰는 일이 드물다.
- B. 카운트에 유효 시간을 둔다. 마지막 숫자 뒤 N초(예: 시퀀스와 같은 1 s, 또는 2 s)가 지나면 버린다.
  - 1의 「한참 뒤」는 풀린다. 짧은 사이의 메뉴 실행은 남는다.
  - vim에는 없는 동작이다.
- C. 메뉴·툴바·팔레트를 앱의 실행 함수 하나로 모으고, 그 함수가 카운트를 먼저 비운다.
  - 팔레트(S2-T4)와 툴바(S2-T5)는 앱이 만들므로 가능하다.
  - 메뉴 막대는 GPUI가 Action을 직접 실행한다. 메뉴 항목을 감싼 Action으로 바꾸면 메뉴에 단축키가 표시되지 않는다(GPUI는 항목의 Action에 걸린 키를 보여 준다).
  - 그래서 메뉴 막대 경로만 1·2가 남는다.
- D. B와 C를 함께 쓴다.

## 권고

C. 팔레트·툴바는 S2-T4·T5에서 실행 함수를 하나로 모으면서 자연히 카운트를 비울 수 있다. 메뉴 막대의 남는 경우는 A처럼 한계로 둔다. B는 vim 사용자의 기대(느리게 쳐도 카운트가 산다)와 어긋난다.

## 결정

C(2026-10-17, YoungTaek). 팔레트(S2-T4)와 툴바(S2-T5)의 실행을 앱의 실행 함수 하나로 모으고, 그 함수가 카운트를 먼저 비운다. 메뉴 막대 경로(경우 1·2)는 한계로 남긴다. 경우 3(대기 만료로 실행된 접두가 카운트를 받음)은 지금 동작을 유지한다. 미룬 테스트는 S2-T4가 이 결정에 맞게 고쳐 켠다.
