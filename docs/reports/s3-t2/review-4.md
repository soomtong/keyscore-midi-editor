## 1. 코드만 읽고 적은 「내가 검사할 것」

`git show fe5d3b5`의 두 파일만 읽고 적었다.

1. 지적 1: `extend`의 클립 우선순위에 `current.track().zip(current.clip())`가 첫 클립 규칙 앞에 들어갔다. 이 규칙은 (a) 선택의 트랙이 현재 트랙인지 보지 않는다. 5.11 「선택을 유지한 채 다음 트랙」 뒤 다른 트랙의 틈에서 넓히면 보이지 않는 트랙의 클립에서 `region_notes`로 노트를 더하는가. (b) 선택의 클립이 직사각형과 겹치는지도 보지 않는다(겹치지 않으면 `region_notes`는 비어 합집합 = 지금 선택이라 해롭지 않아 보인다). (c) 리뷰 3 시도 1의 A·A·B·B가 서는가, B 뒤 틈으로 더 나가도 B가 유지되는가.
2. 제안 4: `picked`가 `None`이면 선택을 둔다. 이제 `None`은 「선택이 비었고 현재 트랙에 걸치는 클립이 없음」일 때뿐이다. 그때도 기준 칸은 남고 `cursor_moved(true)`가 FSM을 맞추는가.
3. 제안 5: `sync_selection_mode`가 `anchor().is_some()`도 선택으로 센다. (a) 기준 칸만 남은 상태에서 `Esc`가 지우고, 두 번째 `Esc`는 아무 일도 없는가(5.8). (b) 수식키 없는 이동이 기준 칸과 컨텍스트를 함께 내리는가(`cursor_moved`에 새로 들어간 `sync_selection_mode`). (c) 뷰 전환: `window.rs:285`의 `apply_mode_event`는 실제 선택이 비어 있지 않을 때만 기준 칸을 지운다. 기준 칸만 남은 상태로 `v`를 누르면 기준 칸이 배치 뷰까지 살아남고, 거기서 문서가 바뀌면(`selection_document_changed` → `sync_selection_mode`) 배치 뷰에 `Select`가 들어가는가. 돌아와 넓히면 옛 기준 칸에서 넓히는가.
4. 지적 2: `save_user`가 디스크의 옛 파일을 다시 읽어 `already`(키 글자 목록)를 만들고 「이미 있는 키」면 예약 키를 통과시킨다. 비교가 키 글자뿐이라 (a) 파일에 손으로 쓴 `f20`이 하나 있으면 다른 Action·다른 컨텍스트에 새로 거는 `f20`도 통과하는가(2회차 지적 6의 거짓 성공이 다시 열림). (b) 손으로 쓴 `F20`(대문자)·`shift-f20`·`g f20`은 `parse`가 글자를 그대로 두므로 다른 편집 뒤에도 남는가. (c) 새로 거는 `alt-F20`은 여전히 거부되는가. (d) 옛 파일을 못 읽거나 문법 오류면 `already`가 비어 예전처럼 전부 거부한다(편집 자체는 `current_layers`가 먼저 막는다).
5. 리뷰 시험 1–3회차 파일이 리뷰어 커밋 뒤 바뀌었는가. 바뀌지 않았다면 수정이 기대값을 약하게 만들 길은 없다.
