# 적대적 리뷰: S0-T8 `ksq-cli` (리뷰 5회차)

- 리뷰어 세션: 구현자·계획자·리뷰 1–4와 다른 새 서브 에이전트 세션. 구현 맥락을 물려받지 않았다.
- 대상 커밋: `8260180` (브랜치 `s0/t8-ksq-cli`). 범위는 리뷰 4 수정 코드 커밋 `340137c`, `7050c0e`뿐이다(`git diff 6b17d05 HEAD -- tools/`).
- 범위 밖: 1–4회차에서 확인된 성질(어림의 위쪽 한계, 손실 보고, 파싱 등)은 다시 훑지 않았다.

## 1. 코드만 읽고 적은 「내가 검사할 것」

`git diff 6b17d05 HEAD -- tools/`의 `cli.rs`와 README, `convert.rs`의 `to_text`·`check_estimate`만 읽고 적었다. 테스트는 리뷰 테스트 diff(0바이트)만 먼저 보았다.

1. 리뷰 1–4 테스트가 그대로인가. 수정을 되돌린 사본에서 리뷰 4 실패 테스트 3개가 다시 실패하는가.
2. `special_output`은 링크를 따라간 경로를 `file_name()`과 `parent()`로 쪼개 부모만 `canonicalize`한다. `Path`의 구성요소 분해는 끝의 `/`와 `.`을 버리므로, `/dev/null/`·`fifo/`처럼 커널이 ENOTDIR로 거부하는 경로를 `/dev/null`·`fifo`로 바꿔 열지 않는가.
3. `file_name()`이 `None`인 경로(`..`로 끝남, `.`, 빈 경로, `/`)와 `canonicalize`가 실패하는 부모(없음, 권한 없음)는 판정 없이 원자적 쓰기로 가는데, 거기서 깔끔하게 실패하고 임시 파일을 남기지 않는가.
4. `..`·`.`가 섞인 상대·절대 링크 사슬, `/dev`를 가리키는 디렉터리 링크 뒤의 `..`, macOS `/tmp`·`/var` → `/private` 별칭에서 판정이 커널의 경로 풀이와 같은가.
5. `Special::Dev`는 일반 파일도 그대로 연다(`allow_regular`). `/dev/` 밖 일반 파일이 이 갈래로 들어가 옛 꼬리가 남는 경로가 다시 생기는가. `/dev/fd/N`이 잘라 쓰지 않고 연 일반 파일이면 어떤가.
6. 안내값 `estimated`는 `check_estimate`의 u128 합을 u64로 자른 값이다(`unwrap_or(u64::MAX)`). 합이 u64를 넘으면 안내값 `u64::MAX`를 주어도 `total <= limit`이 거짓이라 다시 거부되지 않는가.
7. 안내값으로 정말 통과하는가: 표준 출력, `-o`, `.ksqz` 입력. 거부될 때 표준 출력이 비어 있는가. 안전망에서 걸린 경우의 안내가 맞는가.

## 6. 실시간·에러 경로

- 스케줄러 경로의 할당·락·로그: 없음(실시간 경로 없음).
- 제품 코드의 `unwrap`/`expect`: 새로 생긴 것 없음.
- 에러가 삼켜지는 곳: `special_output`의 `.ok()?` 세 곳(`resolve_symlink`, `file_name`, `canonicalize`)은 판정 실패를 「특수 아님」으로 바꾸지만, 원자적 쓰기가 같은 경로를 다시 열어 그쪽 오류로 끝나므로 삼켜지지 않는다(시도 8). 반면 끝의 `/`에 대한 ENOTDIR은 판정이 경로를 고쳐 써서 사라진다(지적 1).
- 경쟁 방어(코드 검토): `write_special`은 `Other`면 잘라 쓰기 없이 연 뒤 핸들의 `metadata().is_file()`로 되돌아가므로, 판정 뒤 일반 파일로 바뀌어도 쓰지 않는다. 디렉터리로 바뀌면 열기가 EISDIR로 실패해 원자적 쓰기로 가지 않고 오류로 끝나는데, 어느 쪽이든 실패라 해롭지 않다. `Dev`에는 이 방어가 없지만 `/dev`(devfs)에 사용자가 일반 파일을 만들 수 없어 경쟁 대상이 없다.
- 안전망 쪽 안내: 안전망에서 걸리면 `estimated`는 실제 크기다. 안전망은 어림 < 실제일 때만 걸리므로, 실제 크기를 상한으로 주면 어림도 그 안이라 두 검사를 다 지난다. 안내가 성립한다(어림이 맞는 한 도달 불가라 실행으로는 확인하지 못했다).
