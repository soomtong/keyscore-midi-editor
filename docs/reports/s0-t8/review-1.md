# 적대적 리뷰: S0-T8 `ksq-cli` (리뷰 1회차)

- 리뷰어 세션: 구현자·계획자와 다른 새 서브 에이전트 세션. 구현 맥락을 물려받지 않았다.
- 대상 커밋: `2f467c3` (브랜치 `s0/t8-ksq-cli`, `git diff main...HEAD` 36파일)

## 1. 코드만 읽고 적은 「내가 검사할 것」

`src/*.rs`와 core `ksq.rs`의 읽기·쓰기만 읽고, `tests/`를 열기 전에 적었다.

1. 손실 보고가 빠지는 속성: 벨로시티(16비트 한 단계 차이 포함), 오프셋, 트랙 속성 6종, 클립 이름·색, 클립 이동·분할·삭제, 템포·박자 변화, 같은 이름. 하나씩만 바꿔도 손실이 나와야 한다.
2. 모르는 키 탐지가 층마다(최상위·조·트랙·포트·클립·노트) 맞는가. 키 목록이 core와 어긋나면 거짓 손실이 나는가.
3. 텍스트 문법과 부딪치는 트랙 이름·가사(따옴표, 줄바꿈, `@track`, `ch2`처럼 보이는 이름, 공백만 다른 이름)가 `Mismatch` 없이 왕복하는가.
4. 출력 증폭: 먼 틱의 클립을 시작 0으로 합치면 앞 빈 곳이 쉼표로 풀린다. 작은 `.ksq`가 거대한 텍스트·메모리가 되는가.
5. `check`의 버전 판정이 core와 같은 값을 보는가: 실수 `2.0`, u64 밖 정수, 같은 키 두 번, BOM, gzip.
6. 입력과 출력이 같은 파일: 상대 경로, `./`, `..`, 심볼릭 링크, 하드 링크, 대소문자만 다른 경로(APFS). 쓰기 실패 시 입력 보존.
7. 인자 경계: `-o` 값 없음, 두 번, 입력 둘, 모르는 옵션, `-` 하나, 비 UTF-8 경로.
8. 픽스처: 8곡이 계획 표대로인지, 정말 8마디인지, 숨김 꼬리가 없는지.
9. `check-deps.sh`의 ksq-cli 규칙 우회: 이름 바꿔 가져오기(`package =`), dev·build 의존.
10. 제품 코드의 `panic`·`unwrap`.

## 6. 실시간·에러 경로

- 스케줄러 경로의 할당·락·로그: 없음(실시간 경로 없음).
- 제품 코드의 `unwrap`/`expect`/`panic`:
  - `fixtures.rs:49` `unwrap_or_else(|e| panic!(…))`: 빌드에 박힌 원본이 엄격 모드로 안 읽힐 때뿐이다. `# Panics` 문서와 `fixtures_sources_read_in_strict_mode_without_warnings`가 지킨다. 받아들인다.
  - `convert.rs:180`, `:259`, `:353`의 `unwrap_or`·`unwrap_or_default`: 주석의 논증(나머지 < 12, 비둘기집, 남는 길이 < u32)이 맞다. 도달 불가.
- 에러가 삼켜지는 곳:
  - `cli.rs`의 `say!`: 표준 오류 쓰기 실패만 무시한다. 의도대로다.
  - `check.rs:102-114`: 버전을 못 읽으면 `None`이고 core 읽기가 오류를 낸다. 시도 8로 확인.
  - `Loss::Mismatch`는 손실 한 줄로만 찍히고 종료 0이다(지적 2).

## 7. 지적 사항

| # | 심각도(차단/수정/제안) | 내용 | 파일:줄 |
| --- | --- | --- | --- |
| 1 | 수정 | 출력 크기에 상한이 없다. 먼 틱의 클립이나 긴 빈 클립을 시작 0 클립 하나로 합치면서 빈 곳을 마디마다 `r1 \|`로 풀어 쓴다. 581바이트 `.ksq`가 5 MB(8,605배), 139바이트가 50 MB에 RSS 657 MB가 됐다. 시작 틱은 u64라 10^12틱이면 5 GB 문자열을 만들고 `verify`가 다시 파싱하므로 메모리를 다 쓴다. `Loss::ClipLayout`은 보고되지만 출력은 그대로 만든다. S0-T5가 텍스트 → 텍스트에 지킨 「선형, 256배 이내」와 맞지 않는다(core도 압축 해제 크기를 512 MiB로 묶는다). 고치는 방향의 예: 합친 클립 길이(또는 내보낼 쉼표 수)에 상한을 두고 넘으면 `CliError`로 거부, 또는 앞 빈 곳을 잘라 첫 클립 시작을 0으로 당기고 손실로 보고(이 경우 `ClipLayout`의 의미가 바뀌므로 계획자 판단). 보고서 「리뷰어에게」 2를 확인한 결과다 | `tools/ksq-cli/src/convert.rs:346`, `:237-238` |
| 2 | 제안 | `Loss::Mismatch`(keyscore-text 버그 신호)가 나도 `ksq2txt`는 종료 0으로 틀린 텍스트를 쓴다. 이번 시도로는 `Mismatch`를 만들지 못했지만, 나면 출력이 원본과 「설명되지 않게」 다르다는 뜻이므로 종료 1(또는 출력 거부)이 안전하다 | `tools/ksq-cli/src/cli.rs:217-219` |
| 3 | 제안 | `ksq2txt -o`는 `fs::write`로 바로 쓴다. 쓰다 실패하면 기존 출력 파일이 잘린 채 남는다. 입력은 안전하지만(같은 파일 판정), `txt2ksq`는 core의 임시 파일 + rename을 쓰므로 두 바이너리의 쓰기 보장이 다르다 | `tools/ksq-cli/src/cli.rs:221` |
| 4 | 제안 | UTF-8 BOM으로 시작하는 텍스트를 `txt2ksq`가 「@track 블록 밖」 오류로 거부한다. 메모장류 편집기가 붙이는 BOM이라 사람이 손으로 쓴 텍스트(출구 게이트 수동 항목)에서 만날 수 있다. 도구가 BOM을 떼거나, text 쪽 결정으로 넘긴다 | `tools/ksq-cli/src/cli.rs:255` |
| 5 | 제안 | `any_project` proptest는 손실 없는 사례가 드물어(클립 0~2개, 시작 절반이 0이 아님, 벨로시티·오프셋·꼬리 무작위) 「손실 없음 ⇒ 바이트 같음」을 거의 시험하지 않는다(보고서 「리뷰어에게」 3). 이번 리뷰가 확정적 변경 17종 테스트로 보완했지만, proptest 쪽도 손실 없는 사례 비율을 `prop_assume`나 분포 조정으로 올리거나 비율을 재 두면 좋다 | `tools/ksq-cli/tests/round_trip.rs:168-211` |

보고서 「리뷰어에게」 1(키 목록 이중 관리)은 시도 5로 확인했다. core가 아는 키는 core가 꺼내 가므로 같은 이름의 모르는 키가 생길 수 없고, 목록이 빠지면 거짓 손실 쪽으로만 틀린다. 지적하지 않는다.
