## 1. 코드만 읽고 적은 「내가 검사할 것」

`802676f`의 `window.rs`(`fit_side_panels`, `requested`, `record_sizes`)와 gpui-base 0.7.2 `resizable`(`ResizablePanel::size`는 첫 그리기의 초기 크기일 뿐이고, 그 뒤에는 상태의 `panel.size`가 이긴다. `size_range`는 `min_w`/`max_w`로 그린 크기를 묶는다)을 먼저 읽고 적었다.

1. `requested`는 그릴 때마다 저장값에서 다시 계산되지만 크기 상태는 창 크기 변경·접기에서만 새로 만든다. 줄어 보이는 동안 한 번 조절해 저장하면 `requested`는 새 저장값의 축소값이 되고 그린 크기는 그대로라 둘이 어긋난다. 다음 조절의 「더 많이 바뀐 쪽」 판정이 낡은 기준으로 틀어지는가.
2. `fit_side_panels`는 범위 최소(120)를 모른다. 축소값이 120보다 작으면 gpui-base가 그린 크기를 120으로 묶어 요청과 그린 크기가 처음부터 다르다. 그 차이가 「끈 패널」로 오인되어 조절하지 않은 패널을 저장하는가.
3. 넓은 창(축소 없음)에서의 일반 조절, 한쪽 패널만 펴진 경우, 줄어 보이는 패널을 접고 펴기, 메인이 최소에 닿아 반대쪽이 밀리는 끌기.
4. room이 0인 아주 좁은 창(시험 플랫폼은 최소 크기를 강제하지 않는다), 범위 밖으로 끌기, 창을 다시 넓혔을 때 저장 크기 복귀.
5. 아래 패널(세로) 조절은 `requested`를 쓰지 않는다. 좁은 창에서 세로 조절이 사이드 패널 저장값을 건드리지 않는가.
6. 두 창: `requested`는 창마다다. 좁은 창 A의 조절이 넓은 창 B가 저장한 값을 되돌리지 않는가.

## 2. 실제 테스트와의 차이

| 내가 검사하려던 것 | 실제 테스트 존재 여부 | 비고 |
| --- | --- | --- |
| 1. 줄어 보이는 동안 두 번째 조절 | 없음 | 리뷰 1 시도 1은 창 크기 변경 직후 한 번만 조절한다 |
| 2. 축소값이 범위 최소 아래 | 없음 | 기존 시험은 500·500(축소값 390)만 쓴다 |
| 3. 넓은 창·한쪽만·접기·밀림 | 부분 | 넓은 창 조절은 기존 레이아웃 시험이, 밀림은 없음 |
| 4. room 0·범위 밖·다시 넓히기 | 없음 | |
| 5. 좁은 창의 세로 조절 | 부분 | 리뷰 1 시도 4는 축소 없는 창 |
| 6. 좁은 창과 넓은 창 | 부분 | 리뷰 1 시도 5는 두 창 모두 축소 없음 |
