# 적대적 리뷰: S0-T6 `.ksq` 직렬화 (리뷰 1회차)

- 리뷰어 세션: 구현자와 다른 세션(리뷰 전용 서브 에이전트, 구현 컨텍스트 없음)
- 대상 커밋: `3bee78f` (브랜치 `s0/t6-ksq`, `main` 대비 커밋 5개)

## 1. 코드만 읽고 적은 「내가 검사할 것」

`ksq.rs`의 `#[cfg(test)]` 위와 `note.rs`·`clip.rs`·`track.rs`·`project.rs` 변경분만 읽고 적었다.

1. 「모르는 키 보존」이 모든 객체에 적용되는가. `read_key`(413행)와 `read_port`(490행)는 필요한 키만 꺼내고 나머지를 버리는 것으로 보인다. `key`·`port` 객체 안의 모르는 키가 남는가.
2. 모르는 키에 담긴 실수가 바이트 그대로 왕복되는가. `serde_json`에 `float_roundtrip` 기능이 없으면 파서가 최선 노력 정밀도라서, 쓴 문자열을 다시 읽으면 다른 `f64`가 될 수 있다.
3. 큰 정수(u64 끝, i64 끝, u64 초과), `-0`, `1e3`, `1.5`가 패닉 없이 오류이거나 안정적으로 왕복되는가. 델타 누적·클립 시작 + 노트 끝의 오버플로.
4. 중복 키 JSON(알려진 키 두 번, 노트 선택 객체의 `offset`·`lyric` 두 번)에서 왕복이 안정적인가. 공개 API로 알려진 키와 같은 이름의 모르는 키를 넣을 수 있는가(`extra` 설정자의 가시성).
5. 빈 가사 `""`, 빈 선택 객체 `{}`, `offset: 0`이 첫 쓰기 뒤 안정적인가.
6. 깊게 중첩된 모르는 값이 스택 오버플로를 일으키는가(`inline`이 재귀).
7. 읽기 시간이 입력 크기에 선형인가. 템포·박자표는 항목마다 `TempoMap::set`(전체 `rebuild`)을 부르고, 노트는 항목마다 `restore_note`가 `Vec::insert`를 한다. 역순 노트·많은 템포 변화에서 O(n²)일 것이다.
8. gzip 폭탄(작은 압축 파일이 거대한 텍스트로 풀림)에서 메모리 상한이 있는가. gzip 뒤 쓰레기 바이트를 어떻게 다루는가.
9. `write_file`: 심볼릭 링크 경로, 상대 경로(부모가 빈 경로), 파일 이름이 없는 경로(`..`, `/`), 같은 경로 동시 쓰기, 원본 권한 보존, 실패 시 임시 파일 정리.
10. 상위 `format_version` 파일을 열고 저장하면 무엇이 기록되는가.
11. 절대 피치 범위(결정 B)가 `with_offset` 말고 다른 공개 경로(음높이 변경)로 깨지는가.
12. 숨김 꼬리와 클립 길이 기본값의 조합, 꼬리가 다음 클립 영역에 걸친 경우 읽기의 겹침 검사.

| 4. 중복 키 | 없음 | |
| 5. 빈 가사·빈 객체 | 없음 | |
| 6. 깊은 중첩 | 없음 | |
| 7. 선형 시간 | 일부 | 정상 순서 10만 노트 벤치만. 템포 다수·역순 노트 없음 |

## 6. 실시간·에러 경로

- 스케줄러 경로의 할당·락·로그: 없음. 이 Task는 파일 입출력만 다루고 스케줄러 코드를 건드리지 않는다.
- 제품 코드의 `unwrap`/`expect`: ksq.rs에 없음. `unwrap_or*`만 있다(113·442·513·529행, 모두 기본값). `items[i]`(571행)는 564행의 길이 검사(4–5) 뒤에 0–3만 쓴다.
- 에러가 삼켜지는 곳:
  - ksq.rs:207 노트 `extra` 문자열을 다시 파싱하다 실패하면 조용히 버린다. `extra`는 crate 안에서 `inline()` 출력으로만 만들어져 실제로는 실패하지 않는다.
  - ksq.rs:757 실패 후 임시 파일 지우기 실패 무시(의도, 주석 있음).
  - ksq.rs:773 디렉터리 fsync 실패 무시(의도, 주석 있음).
  - ksq.rs:727-732 gzip 첫 멤버 뒤의 바이트를 무시한다(지적 9).
