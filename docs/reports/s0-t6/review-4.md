# 적대적 리뷰: S0-T6 `.ksq` 직렬화 (리뷰 4회차)

- 리뷰어 세션: 구현자와 다른 세션(적대적 리뷰어 역할). 제품 코드는 수정하지 않았다.
- 대상 커밋: c04f237 (리뷰 3 이후 diff는 b43b40c `core: Create .ksq temp files with the original mode on Unix`와 plan 기록 1개). 리뷰 3의 권고에 따라 범위를 지적 1 수정과 자동 게이트 유지로 좁혔다.

## 1. 코드만 읽고 적은 「내가 검사할 것」

1. 원본이 있으면 `OpenOptionsExt::mode(원본 & 0o777)`로 만든다. umask가 더 좁히면 만들어진 임시 파일은 원본보다 좁다. 이후 `set_permissions`가 원본 권한으로 넓힌다. 이때 넓어지는 상한이 원본이므로 원본보다 넓은 순간은 없어야 한다.
2. umask 077에서 0644 원본: 생성 시 0600, 이후 0644로 복구되는가. 최종 권한이 원본과 같은가.
3. 원본 0444 / 0400 / 0000: `create_new`는 새 파일 생성이라 mode가 읽기 전용이어도 열린다. 쓰기는 이미 연 핸들로 하므로 성공해야 한다.
4. 원본이 없는 새 파일: `original`이 None이라 mode를 설정하지 않아야 한다. 0600이나 0777이 되면 안 되고 0666 & !umask여야 한다.
5. `& 0o777`로 setuid/sticky 비트를 떼고 만들지만, 뒤의 `set_permissions(meta.permissions())`는 전체 비트를 복구한다. 의도된 동작인지, 권한이 늘어나는 방향은 아닌지.
6. 다른 소유자의 파일: 임시 파일은 호출자 소유로 생기고 rename으로 대체된다. 이는 이번 변경 이전부터의 동작이며 이번 변경이 악화시키지 않는지.
7. 비유닉스: `#[cfg(unix)]`가 `if let` 문에 붙었다. `let mut options`가 비유닉스에서도 쓰이는지(경고 없음), `original`이 두 분기에서 이동·참조되는 방식이 컴파일되는지.
8. `fs::metadata(path)`가 `open`보다 먼저 호출된다. 메타데이터를 읽은 뒤 원본이 바뀌는 TOCTOU는 어떤 결과를 내는가.
9. 리뷰 3 재현 테스트가 스레드 타이밍에 의존하므로, 수정 후 여러 번 돌려도 통과하고 수정 전에는 안정적으로 실패하는지.

## 2. 실제 테스트와의 차이

| 내가 검사하려던 것 | 실제 테스트 존재 여부 | 비고 |
| --- | --- | --- |

| 원본 0444/0000 등 | 없었음 | 이번에 추가 |
| 새 파일 권한 | 없었음 | 이번에 추가 |
| 비유닉스 컴파일 | 없음 | 설치된 타깃이 `aarch64-apple-darwin`뿐이라 실행 불가. 코드 읽기로만 확인 |

## 6. 실시간·에러 경로

- 스케줄러 경로의 할당·락·로그: 없음(파일 입출력 경로).
- 제품 코드의 `unwrap`/`expect`: 이번 diff에서 추가된 것 없음.
- 에러가 삼켜지는 곳: `fs::metadata(path).ok()`가 모든 오류(권한 거부 포함)를 「원본 없음」으로 취급한다. 부모 디렉터리 접근 불가면 어차피 뒤의 `open`/`rename`이 실패하므로 실해는 없다. 디렉터리 fsync 실패 무시와 임시 파일 삭제 실패 무시는 기존대로이며 주석에 이유가 있다.
