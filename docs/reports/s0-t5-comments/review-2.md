## 1. 코드만 읽고 적은 「내가 검사할 것」

`parse.rs`의 `run`·`directive`·`tempo`·`time`·`key`·`track_header`와 `lenient`를 읽고, 테스트 파일을 열기 전에 적었다.

1. 헤더 값 바로 뒤에 공백 없이 붙은 `#`(`@tempo 120#`, `@time 4/4#`, `@key C major#`)가 `run`의 헤더 영역 분기로 가서 두 모드 오류, 위치는 `#` 자리, 메시지에 「주석은 //」가 붙는가. `@key C# minor # x`에서 으뜸음 `#`는 올림표로 먹고 뒤의 `#`만 오류인가.
2. 두 `@track` 블록 사이의 `#` 줄은 `voice`가 이미 있으므로 첫 트랙 본문으로 읽혀 느슨 모드 경고, 엄격 모드 오류인가. 둘째 트랙이 정상으로 이어지는가.
3. `@track A ch1 # 메모`처럼 `@track` 줄 끝의 `#`도 트랙 안 규칙(경고/오류 + 안내)인가. `prog0#`처럼 붙은 경우도.
4. BOM + `#`: keyscore-text는 BOM을 떼지 않으므로 BOM 자리 오류이고 안내가 없을 것이다. ksq-cli는 BOM을 뗀 뒤 `#` 안내 오류를 내는가.
5. 헤더 영역의 `#` 아닌 모르는 토큰(음, 홑 `/`, 글자)에 `#` 안내가 잘못 붙지 않는가. 트랙 안 홑 `/` 경고에도 붙지 않는가.
6. 헤더 값 자리(`@tempo # 120`, `@key C #`)의 `#`는 무슨 메시지인가. 결정 문구 「`#`에 대한 경고·오류에는 안내」와 어긋나는가.
7. 결정 Q1 개정 줄, 보고서의 「바뀐 동작」 표·「리뷰어에게」·「리뷰 대응」이 위 동작과 모두 맞는가.
8. `hash_before_first_track_is_lenient_warning` → `hash_before_first_track_is_error_with_slash_hint` 수정이 리뷰 1이 낸 (b)를 그대로 따르는가, 검사가 약해지지 않았는가.

## 2. 실제 테스트와의 차이

| 내가 검사하려던 것 | 실제 테스트 존재 여부 | 비고 |
| --- | --- | --- |
| 1. 헤더 값에 붙은 `#` | 부분 | 고친 리뷰어 테스트는 공백 뒤 `#`(`@tempo 120          # 선택`, `@key C major # 선택`)와 줄 첫머리만. 붙은 경우와 위치 검사 없음 |
| 2. 트랙 사이 `#` 줄 | 없음 | |
| 3. `@track` 줄 끝 `#` | 있음 | 리뷰 1 `hash_in_token_positions_inside_track_is_unknown`(`@track A ch1 #`, `bank0#`). 안내 문구 검사는 없음 |
| 4. BOM + `#` | 없음 | ksq-cli `cli.rs`에 BOM 하나·둘 테스트가 있으나 `#`와 겹친 경우는 없음 |
| 5. 다른 토큰에 안내가 붙지 않음 | 없음 | |
| 6. 헤더 값 자리 `#` | 없음 | |
| 7. 문구 | 해당 없음 | 수동 대조 |
| 8. 리뷰어 테스트 수정 | 있음 | 두 모드 `unwrap_err`와 메시지의 `//` 검사 |

리뷰어 테스트 수정의 정당성(B)
- 리뷰 1이 낸 방법 (b)는 「헤더 영역의 오류를 의도로 결정·보고서 문구를 좁히고 `#`일 때 `//` 안내를 메시지에 넣는다」였다. 고친 테스트는 두 모드 오류와 메시지의 `//`를 검사해 (b)를 그대로 옮겼다. 입력 셋은 그대로이고 엄격 모드 검사는 남았으며 느슨 모드 검사는 「성공」에서 「안내 있는 오류」로 바뀌었을 뿐 약해지지 않았다. 「구현자 수정」 주석으로 바꾼 이유를 남겼다. 정당하다.
- 결정 문서는 (b)의 요구대로 코드보다 먼저(같은 커밋 묶음 안에서) 고쳐졌고 사람이 쓴 개정 인용문은 손대지 않았다. 21–24행이 코드와 정확히 맞는다(시도 1–3).
- 보고서의 「바뀐 동작」 표 두 행과 「리뷰 대응」 표는 코드와 맞는다. 맞지 않는 곳은 지적 1 하나다.
