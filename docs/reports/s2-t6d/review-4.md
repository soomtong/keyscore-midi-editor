## 1. 코드만 읽고 적은 「내가 검사할 것」

1. 지적 1: 정지 중(`!has_owner()`)이고 풀린 추가 포트가 있으면 기본 포트만 든 스냅샷으로 바꾼 뒤 재등록한다. 정지 뒤 첫 서버 확인에서 실제로 다시 등록되고 알림이 남는가.
2. 재생 중에는 스냅샷을 바꾸지 않는가(재생 상태, 기본 포트 소리, 풀린 포트는 그대로).
3. 정지 중 교체가 다음 재생·정지 중 테스트 노트를 망가뜨리는가. 재생 시작(`play_from`)과 정지 중 테스트 노트는 모두 `prepare`로 스냅샷을 새로 넣으므로 영향이 없어야 한다. 메트로놈은 재생 시작 때 `set_metronome`을 다시 보낸다.
4. 200 ms 기다림: 교체 뒤 `Arc::strong_count > 1`인 동안만 돈다. 추가 포트의 다른 `Arc`는 스냅샷 말고 `opened`·`retired`에 들어가지 않으므로(`open_port`는 `extras`에서 복제해 스냅샷에만 넣는다) 교체가 들어가면 곧 1이 된다. 풀린 포트가 계속 풀린 경우(재등록 실패)에도 기다림은 짧아야 한다. 기다림을 다 쓰는 것은 교체가 들어가지 않을 때(큐 가득, 스케줄러 스레드 끝남)뿐이다.
5. 풀린 포트가 없으면 교체하지 않는가(`lost` 거짓이면 이전과 같다).
6. 제안 2: 대체 이름이 목적지와 설정의 추가 포트 모두를 피하는가. 첫 후보와 둘째 후보가 모두 추가 포트면 셋째로 가는가. 설정의 `main_name`·`virtual_ports`는 그대로인가.
7. 제안 3: `!edits.is_empty() && w.edit_document(edits, cx)`. 편집 성공 때만 `owner_edited`가 서고, 실패면 `ports_edited`가 재생 창을 교체한다. 편집 없음(빈 목록)일 때는 이전과 같다.

## 6. 실시간·에러 경로

- 스케줄러 경로의 할당·락·로그: 없음.
- 제품 코드의 `unwrap`/`expect`: 새로 든 것 없음.
- 에러가 삼켜지는 곳: `reregister_extras`의 교체 실패(`let _ = self.scheduler.swap(...)`, `engine.rs:660`). 실패하면 기다림 200 ms를 다 쓰고, 풀린 포트가 그대로면 다음 서버 확인(정상 1초마다)에서 또 그렇다. 교체가 실패하는 것은 명령 큐가 차거나 스케줄러 스레드가 끝난 경우뿐이라 제안으로 둔다(지적 1). 시도 1에서 정상 경로의 서버 확인 한 주기는 200 ms 미만이었다.
- 코드 읽기: 정지 중 교체는 바뀐 포트의 미리듣기 노트를 바로 끈다(`scheduler.rs` `swap`의 정지 분기). 풀린 추가 포트가 있는 동안 정지 중 서버 확인과 겹친 테스트 노트(이름 포트, 200 ms)가 짧게 끊길 수 있다. 걸린 노트는 남지 않고 드문 겹침이라 지적하지 않는다.
