# 적대적 리뷰: S3-T5c 드럼 트랙의 조성 명암 제외와 건반 뷰 라벨 넘침 (리뷰 2회차)

- 리뷰어 세션: 구현자와 다른 세션(적대적 리뷰 서브 에이전트, 구현 컨텍스트를 물려받지 않음). 직전 수정 범위로 좁힌 확인 리뷰
- 대상 커밋: 9dba2db (수정 커밋 5607dbb 「Draw at most three-letter names on black keys」)

## 1. 코드만 읽고 적은 「내가 검사할 것」

수정 diff(`keyboard_view_window.rs` 한 줄 `.filter(|n| !cap.black || n.chars().count() <= 3)`)와 `render_keyboard_view`, `accessible`, `keys`만 읽고 적었다. 1회차 리뷰 시험 파일은 헬퍼를 빌리려고 읽었고, 구현자 시험은 이번 수정에서 바뀌지 않았다.

1. 드럼 트랙, 옥타브 0~9, 건반형·계이름형, 창 크기(기본·넓음·중간·최소 720×480) 전부에서 검은건반 이름 글이 「글 + 4 px ≤ 건반」인지(1회차 기준).
2. 그리지 않는 네 글자 이름(`n100`~`n127`)이 `keyboard-key-<i>`의 접근성 라벨에는 「이름 키」 그대로 남는지. `accessible(cap)`은 `cap.name`을 쓰고 필터는 `drawn_name`에만 걸려 있으니 남아야 한다.
3. 필터가 지나치게 걸러 세 글자 이하 검은건반 이름(`n61`, `n99` 등)이나 흰건반 이름을 지우지 않는지. 경계 `n99`(그림)와 `n100`(안 그림).
4. 흰건반의 네 글자 드럼 라벨(`n100` 등, 글씨 `text_xs`)이 최소 창에서 흰건반 안에 들어가는지. 필터는 검은건반에만 걸린다.
5. 멜로디 트랙 회귀: 이름은 C 건반(흰건반)에만, `C-1`(세 글자)도 넘치지 않는지. 모든 창 크기·레이아웃·옥타브.
6. 건반 너비가 창 크기 말고 다른 것(트랙 목록·인스펙터 패널 너비)에 따라 24 px 아래로 줄 수 있는지.
7. 필터를 빼면 새 시험이 실제로 실패하는지(변이).

## 2. 실제 테스트와의 차이

| 내가 검사하려던 것 | 실제 테스트 존재 여부 | 비고 |
| --- | --- | --- |
| 1. 모든 옥타브·레이아웃·창 크기의 검은건반 넘침 | 있음(1회차 리뷰 시험 `review_s3_t5c.rs` 4개, PR에 포함) | 기본·넓음·최소 창. 중간 창(1000×700)은 이번 리뷰 시험으로 보강 |
| 2. 그리지 않는 이름이 접근성 라벨에 남음 | 없음 | 보고서는 근거로 `review_s3_t5_r2::accessible_labels_match_model_for_every_key`를 들었지만 그 시험은 `project(1)`, 즉 멜로디 트랙만 본다. 드럼 네 글자 라벨은 덮지 않는다. 리뷰 시험으로 보강 |
| 3. 세 글자 이하·흰건반 이름을 지우지 않음 | 없음 | 넘침 시험은 「그린 글이 넘치지 않음」만 보므로 아무것도 그리지 않아도 통과한다. 리뷰 시험으로 보강 |
| 4. 흰건반 네 글자 라벨 넘침 | 없음 | 1회차 리뷰 시험·구현 시험 모두 흰건반은 건너뛴다(구현 시험은 oct2·3만). 리뷰 시험으로 보강 |
| 5. 멜로디 회귀 | 부분(`melody_black_keys_draw_no_name`, 검은건반만) | 흰건반까지 모든 창·레이아웃·옥타브로 보강 |
| 6. 패널 너비에 따른 건반 너비 | 해당 없음 | 코드 읽기: 하단 영역은 `v_resizable`의 아래 패널이라 창 전체 너비를 쓴다(`window.rs:1295-1310`). 트랙 목록·인스펙터는 위쪽 `h_resizable` 안에만 있다. 최소 창 720에서도 흰건반이 상한 40 px라 검은건반은 24 px 고정 |
| 7. 변이 | 없음 | 리뷰에서 실행 |

## 3. 깨뜨리기 시도

| # | 시도 | 결과(깨짐/못 깨뜨림) | 추가한 테스트 |
| --- | --- | --- | --- |
| 1 | 1회차에 실패한 리뷰 시험 4개(건반형·계이름형·기본 창·최소 창) 재실행 | 못 깨뜨림(10개 모두 통과) | (1회차 `review_s3_t5c.rs`) |
| 2 | 드럼 트랙, 창 4종(기본·2400×1400·1000×700·720×480) × 레이아웃 2종 × 옥타브 0~9, 흰건반·검은건반 모두 「글 + 4 px ≤ 건반」 | 못 깨뜨림 | `drum_names_fit_every_key_window_layout_octave` |
| 3 | 같은 것을 멜로디 트랙(채널 1)으로 | 못 깨뜨림 | `melody_names_fit_every_key_window_layout_octave` |
| 4 | 드럼, 레이아웃 2종 × 옥타브 0~9, 건반 24개 전부: 접근성 라벨 = 「이름 키」, 검은건반은 세 글자 이하면 그리고 네 글자면 안 그림, 흰건반은 길이와 무관하게 그림. 빈 집합이 아님(숨긴 검은건반, 흰건반 네 글자, 검은건반 세 글자가 각각 1개 이상)도 확인 | 못 깨뜨림 | `drum_hidden_black_names_keep_accessible_label` |
| 5 | 변이: 새 필터 `.filter(\|n\| !cap.black \|\| n.chars().count() <= 3)` 제거 | 시도 2·4의 시험이 실패(예: `default p oct6 18 black=true Some("n102"): 글 22 건반 24`). 멜로디 시험은 통과(멜로디는 검은건반 이름이 없어 해당 없음). 되돌림 확인 | (위 시험) |

시험의 한계: 헤드리스 시험 창은 `NoopTextSystem`을 쓰며 모든 글자 폭을 0.6 em으로 잰다. 그래서 시험이 보는 것은 실제로는 「글자 수 × 글씨 크기」다. 검은건반 세 글자(9 px)는 16.2 px로 여유가 7.8 px라 실제 글꼴의 폭 차이(드럼 라벨은 소문자 두 자이거나 `n` + 숫자)로 넘칠 가능성은 낮다. 실제 글꼴 폭은 확인하지 않았다(앱 실행 금지).

1회차 제안 2·3을 고치지 않은 이유 검토:

- 제안 2(피아노롤 장면의 창 수준 시험): 시험만을 위해 공개 API를 열지 않는다는 이유는 저장소 규칙(범위 밖 코드를 건드리지 않음)과 맞다. 장면 단위 시험(`scene_rows_on_drum_track_ignore_key`, 1회차 `scene_rows_shade_by_channel_and_key_everywhere`)이 드럼 분기를 잡고, 장면 입력이 `current_track()`이라는 점은 코드로 확인된다. 타당하다.
- 제안 3(창의 실제 색 경로): 헤드리스 시험은 칠한 색을 읽지 못한다. `shades_key` 단위 시험이 판정을 잡고 창은 그 결과를 `key_fill`에 넘기기만 한다. 타당하다. 「실제 창 확인」은 이 리뷰에서 재현하지 않았다(앱 실행 금지).
