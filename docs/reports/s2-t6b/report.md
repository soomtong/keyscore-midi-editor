## 알려진 한계

- 오버레이는 연 때의 모드 경로를 쓴다. 열린 동안에는 모드가 바뀌지 않는다(오버레이가 포커스를 가진다).
- 키 표기는 GPUI 표기(`ctrl-alt-u`)다. macOS 기호(⌃⌥) 표기와 `Kbd` 컴포넌트 모양은 S8 다듬기에서 본다.
- 명령 표에 없는 바탕 레이어 키(gpui-component의 입력란 키 등)는 보이지 않는다.

## 리뷰어에게

- 「실제로 동작하는 키」 판정(`bindings_for_input`의 첫 결과와 같은가)이 접두 시퀀스(`g g`)·대기 중 바인딩에서 맞는지.
- 오버레이가 열린 동안 키가 문서로 새지 않는지, 닫은 뒤 포커스.

## 리뷰 1 대응

| 리뷰 항목 | 대응 |
| --- | --- |
| 지적 1: 오버레이가 열린 채 팔레트를 열면 둘이 함께 떠 포커스가 어긋난다 | 팔레트를 열 때 오버레이를 닫는다(팝업과 같은 「하나만 띄운다」) |
| 지적 2: 열린 채 전역 `ctrl-tab`으로 모드가 바뀌면 옛 모드 키를 보인다(UI-6) | 연 때의 경로를 고정하지 않고 지금 모드의 경로를 쓴다. 줄은 (키맵 판, 모드 경로)가 바뀔 때만 다시 구한다 |
| 지적 3: 인자 있는 Action을 이름으로만 묶어 어느 키가 어느 길이인지 사라진다 | 명령 표의 변형(팔레트 줄)마다 따로 둔다(「Step 길이 · 온음표」). 변형이 없는 열린 인자는 Action 표기를 붙인다 |
| 지적 4: 11절의 `Sheet`/`Popover` + `Kbd`를 따르지 않는다 | 키는 gpui-component `Kbd`로 그린다. 그릇은 `Popover` 모양(테마의 popover 배경·테두리)의 가운데 패널이다. `Popover`는 누른 요소에 붙어 뜨는데 `?`에는 그런 요소가 없고, `Sheet`는 자기 포커스·Esc 처리를 가져 `Overlay` 컨텍스트(쪽 넘김, A13 Esc)와 겹친다. 11절 표의 「`Sheet` 또는 `Popover`」를 모양 지침으로 읽은 것이라 REQ 뜻은 바뀌지 않는다 |
| 제안 5: 줄 계산이 그릴 때마다 모든 바인딩을 다시 훑는다 | 키맵 판·모드 경로가 같으면 지난 결과를 쓴다 |
| 제안 6: 열린 동안 `cmd-z` 같은 전역 단축키가 아래 문서를 바꾼다 | 알려진 한계로 둔다. 표준 단축키는 어느 포커스에서나 동작하는 것이 macOS 관례다 |
| 제안 7: 열린 동안 `?`로 닫히지 않는다 | `Overlay` 컨텍스트에 `?` → `help::KeymapOverlay`(열기/닫기)를 걸었다 |
| 제안 8: 처리되지 않은 Action이면 다음 바인딩으로 넘어가는 GPUI 동작 | 지금 키맵에 사례가 없어 알려진 한계로 둔다 |

부록 A1–A3 테스트는 `tests/review_s2_t6b.rs`로 옮겨 통과한다. 깨지지 않은 시도 `question_mark_inside_overlay_does_not_leak`는 제안 7 대응으로 `?`가 오버레이를 닫으므로 그 동작을 보게 고쳤다(열린 동안 `m`이 새지 않는 검사는 그대로).
