# 적대적 리뷰: S1-T6 SMF 입출력 (리뷰 1회차)

- 리뷰어 세션: 구현 세션과 다른 새 서브 에이전트 세션. 구현 컨텍스트를 물려받지 않았다.
- 대상 커밋: a5e343f (브랜치 `s1/t6-smf`, `main..HEAD`)
- 깨뜨리는 테스트: `crates/keyscore-midi/tests/review_s1_t6.rs`

## 1. 코드만 읽고 적은 「내가 검사할 것」

`src/smf/raw.rs`, `src/smf/song.rs`, core `tempo.rs`·`meter.rs` 추가분만 읽고, `tests/smf.rs`를 열기 전에 적었다.

1. 거짓 길이 필드(헤더 길이 4 GB, 청크 길이, 메타·SysEx 길이)가 `Truncated`로 끝나는가. 선언 트랙 수보다 청크가 적을 때, 모르는 청크가 수만 개일 때.
2. running status 남용(데이터 바이트만 수백만 개)이 선형인가. 상태 없이 시작하는 데이터, 0xF4 같은 시스템 공통 상태, 채널 메시지 안의 8비트 데이터.
3. `SongTrack::add_note`는 `partition_point` + `Vec::insert`다. Note Off 순서가 시작 순서와 어긋나는 파일에서 삽입이 매번 뒤쪽을 밀어 이차 시간이 되는가.
4. `Song::attach_lyrics`는 가사마다 모든 곡 트랙을 훑는다. 곡 트랙 16384개(1024 × 16) × 가사 수십만 개면 이차인가.
5. `to_project`가 클립마다 `Track::insert_clip`을 부르고, 그 겹침 검사는 모든 클립을 훑는다. 한 마디 걸러 노트가 있는 파일이면 클립 수의 제곱인가.
6. `put_delta`는 28비트를 넘는 델타를 빈 텍스트 메타로 채운다. PPQ 1에서 큰 델타는 960배 틱이 되므로 다시 쓸 때 출력이 입력의 수백 배로 불어나는가. 공개 API로 u64 끝 가까운 틱을 넣으면 멈추거나 OOM인가.
7. `upscale`이 MIDI 2.0 min-center-max 알고리즘과 7·14비트 전 값에서 같은가.
8. `bar_groups`: 마디 중간 박자 변화(짧은 마디), 마디선에서 정확히 끝나는 노트, 빈 마디로 나뉜 클립, 클립 겹침·노트가 클립 밖으로 나가는 경우.
9. 쓰기의 결정성: SMF → 곡 → SMF가 고정점에 도달하는가.
10. 가사: 같은 틱의 여러 가사(화음에 가사 둘)가 모델 왕복에서 살아남는가. 낮은 음의 가사가 높은 음으로 옮겨지는가.
11. 노트도 프로그램도 없는 모델 트랙이 내보내기 → 가져오기에서 사라지는가.
12. `make_note`의 길이 `u32` 포화: PPQ 1과 큰 틱이면 노트 길이가 조용히 잘리는가.

## 6. 실시간·에러 경로

- 스케줄러 경로의 할당·락·로그: 없음. `scheduler.rs`의 변경은 `beat_at_or_after`가 `next_change_after`(이분 탐색, 할당 없음)를 쓰도록 바꾼 것뿐이다.
- 제품 코드의 `unwrap`/`expect`: 없음. `unwrap_or`만 있다. 그 가운데 `song.rs:565`(노트 길이 `u32` 포화)와 `raw.rs:238`(트랙 수 `u16` 포화로 65535개 넘는 트랙을 버림)은 값을 조용히 바꾼다(지적 7).
- 에러가 삼켜지는 곳: `song.rs:231-241` 잘못된 템포·박자표 메타를 건너뜀(의도, 주석 있음). `Song::from_smf`는 `Result`이지만 `Err`를 내지 않는다.

## 7. 지적 사항

| # | 심각도(차단/수정/제안) | 내용 | 파일:줄 |
| --- | --- | --- | --- |
| 1 | 수정 | Note Off 순서가 시작 순서와 어긋나는 파일에서 `SongTrack::add_note`의 정렬 삽입이 매번 뒤쪽 노트를 밀어 가져오기가 이차 시간이다. 이벤트 180만 개(상한 안)에서 32 s(디버그). 트랙을 다 모은 뒤 한 번 정렬하는 등으로 선형 로그로. 테스트 `interleaved_note_off_order_imports_in_bounded_time` | `song.rs:83-86`, `512` |
| 2 | 수정 | `attach_lyrics`가 고아 가사마다 모든 곡 트랙을 훑어 (가사 수 × 곡 트랙 수)다. 곡 트랙 16368개 × 가사 20만 개에서 51 s. 테스트 `orphan_lyrics_with_many_song_tracks_attach_in_bounded_time` | `song.rs:273-290` |
| 3 | 수정 | `to_project`가 클립마다 `Track::insert_clip`을 부르고 겹침 검사가 모든 클립을 훑어 클립 수의 제곱이다. 두 마디마다 노트 하나인 7만 노트 파일에서 45 s. 클립은 이미 시작 순이고 서로 겹치지 않으므로, 맨 뒤 클립만 보고 붙이는 경로(core 쪽 API 추가는 결정 필요 시 계획에 적기)가 필요하다. 테스트 `sparse_bar_notes_build_many_clips_in_bounded_time` | `song.rs:357`, core `track.rs:348-354` |
| 4 | 수정 | 쓰기 출력이 입력과 무관하게 커진다. PPQ 1의 델타 2^28−1은 960배 틱이 되고 `put_delta`가 28비트마다 채움 메타를 넣어 14 KB 입력이 13.4 MB로, 상한까지 채운 14 MB 입력은 13 GB로 쓰인다. 공개 API(`SongNote::new(Tick::new(u64::MAX − n), …)`)로는 채움 메타 2^36개(약 480 GB)라 사실상 멈춤·OOM이다. 곡 길이 상한(가져오기에서 `Err`, `to_smf`에서 거부)이 필요하다. 테스트 `low_ppq_huge_delta_does_not_amplify_written_size` | `raw.rs:443-450`, `song.rs:219`, `408-409` |
| 5 | 제안 | 같은 틱에 가사가 둘 이상이면 `to_project`가 첫 가사만 가장 높은 음에 붙이고 나머지를 버린다. 모델 → SMF → 모델에서 화음의 낮은 음 가사가 높은 음으로 옮겨지고 다른 가사는 사라진다(시도 12). 같은 틱 노트를 높은 음부터 차례로 짝지으면 줄일 수 있다. 보고서 한계 5에 「같은 틱 둘째 가사 버림」도 적기 | `song.rs:698-706` |
| 6 | 제안 | 노트·프로그램·뱅크가 없는 모델 트랙은 내보내면 이름 메타만 남고, 가져올 때 채널 메시지가 없어 트랙이 사라진다(시도 12). 보고서 한계에 적거나 채널 트랙임을 남길 방법을 정하기 | `song.rs:257-263`, `613-624` |
| 7 | 제안 | 값을 조용히 바꾸는 포화: 재배율한 노트 길이가 `u32`를 넘으면 `u32::MAX`로(`song.rs:565`), 곡 트랙이 65535개를 넘으면 `write`가 나머지를 버린다(`raw.rs:238-241`). 지적 4의 길이 상한과 함께 `Err`로 바꾸는 편이 낫다 | `song.rs:565`, `raw.rs:238-241` |
