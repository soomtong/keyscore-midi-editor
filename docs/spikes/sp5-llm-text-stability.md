# SP-5 소형 LLM의 계이름 텍스트 안정성

측정 일시: 2026-10-11 23:36–23:42 (KST, macOS, 이 기기에서 OpenRouter로 직접 호출). 네트워크: 유선/무선 구분은 확인 못 함. `curl` 기준 openrouter.ai까지 TCP 연결 15 ms, TTFB 51 ms로 왕복 지연은 작은 편이다. 호출 수는 본 측정 100회(+ 모델별 사전 점검 약 10회). 계획의 60회에 reasoning 끈 설정 40회를 더했다.

## 질문

`openai/gpt-5.6-luna`, `~anthropic/claude-haiku-latest`, 로컬급 소형 모델 1종이 REQ 5.14 문법으로 8마디 멀티트랙을 얼마나 안정적으로 내는가. 파싱 성공률 90% 미만이면 기본값에서 제외하고, 실패가 문법 자체의 모호함에서 오면 S0-T5 문법을 손봐야 한다.

## 방법

모델 ID

- `openai/gpt-5.6-luna`와 `~anthropic/claude-haiku-latest`는 `/api/v1/models`에 정확히 같은 ID로 있었다.
- 로컬 모델 몫은 `google/gemma-3-12b-it`(12B 오픈 웨이트, Ollama·LM Studio로 로컬 실행 가능한 크기)를 OpenRouter 경유로 측정했다. 로컬 런타임(Ollama 등)이 이 기기에 없어 로컬 실행 실측은 확인 못 함. 양자화·로컬 하드웨어 속도는 반영되지 않았고, 응답 시간은 OpenRouter 호스팅 기준이다.

프롬프트와 픽스처 (모두 `spikes/sp5-llm-text-stability/`)

- `prompts/system.md`: 영어 시스템 템플릿 초안. 출력 규칙, 문법 요약, 드럼 라벨 표, 검증기를 통과하는 few-shot 두 개(4/4 3트랙, 3/4 가사).
- `prompts/task_new.md`: 과제 템플릿(`{{bars}}` `{{tempo}}` `{{time}}` `{{key}}` `{{tracks}}` `{{request}}` 치환). 요청 문장은 한국어.
- `fixtures/fixtures.json`: 8마디 과제 4종. 모두 기대 마디 수 8.

실행: 픽스처 4 × 모델 3 × 5회, 스트리밍, temperature 0.7, max_tokens 2500, 동시 3건. 스트리밍 응답의 시작~끝을 응답 시간으로 쟀다. 처음 60회를 돌려 보니 두 상용 모델이 기본으로 reasoning(사고) 토큰을 1,000–2,500개씩 쓰고 있어, 앱이 어시스트를 위해 끌 설정(`reasoning.enabled=false`)으로 두 모델을 20회씩 더 돌렸다. 그래서 설정이 둘이다: `rdefault`(OpenRouter 기본), `rnone`(reasoning 끔). gemma는 reasoning이 없어 `rdefault` 한 벌이다.

검증기: `ksparse.py`(Python, `-I`로 실행). 요약은 `python3 -I summarize.py`. 원시 응답과 파싱 결과는 `runs/*.json`(100개)에 있다. API 키는 환경변수에서만 읽고 어떤 산출물에도 쓰지 않았다(`sk-or` 문자열 검색 0건).

검증기가 간략화한 부분

- 길이는 틱이 아니라 Fraction(전음표 단위)으로 센다. 틱 반올림은 다루지 않는다.
- 느슨한 가져오기 모드가 없다. 모르는 토큰은 전부 오류다(AI 응답을 엄격하게 본 것).
- `~±틱`, `v<n>`, 코드펜스, `@track` 밖의 설명문은 AI 응답 금지 규칙에 따라 오류로 본다.
- 옥타브는 `o0–9` 범위만 보고 음역 접기는 하지 않는다. 드럼 `n<번호>`는 35–81 범위만 확인한다.
- `#`는 음이름 바로 뒤에 붙으면 올림표, 그 밖은 주석으로 해석한다(아래 문제 1).
- 마디 수는 두 가지로 센다: 누적 길이 / 마디 길이(길이 기준), `|`로 나뉜 구간 수(마디선 기준). 마디마다 길이가 맞는지는 별도 경고로 본다.

지표 정의

- 파싱 성공: 문법 오류 0건. 기대 트랙·채널이 빠지거나 다르면 구조 문제로 따로 센다.
- 마디 수 일치(bars_ok): 파싱 성공, 구조 문제 0건, 모든 트랙의 누적 길이가 정확히 8마디.
- exact: bars_ok이면서 모든 마디가 정확히 마디 길이.
- pipe_ok: 파싱 성공, 구조 문제 0건, 모든 트랙이 `|` 기준 8구간.

대표 실패 유형

- haiku [rdefault]의 실패 6건은 문법 오류가 아니라 잘림이다. reasoning이 2,500 토큰을 다 써서 본문이 비었다(`finish=length`가 9건, 그중 본문 0자가 6건). 잘리지 않은 11건은 11/11 파싱 성공이다. max_tokens를 사고 예산만큼 키우거나 reasoning을 제한하면 사라질 실패다.
- 음 뒤 숫자를 과학적 음높이(옥타브)로 쓴다: `d6`(haiku rnone 4건, 길이 5도 1건), `c3`(gemma 6건). MML에서 `d6`은 길이 6이라 오류다. 모델이 `c4`를 가온다(C4)로 읽는 관습에 끌린다.
- LilyPond/ABC식 방언: 옥타브 `c'` `d'` `g'`(gemma 3건, gpt rnone 2건, haiku 2건), `b,` `g,`(gemma 2건, haiku 2건). 독일식 올림표 `fis` `cis`(gpt rnone 4건, D 장조 f4에서 반복).
- 모델의 자기 정정 문장이 출력에 섞임(haiku rnone, 예: `c'? Wait, I must not include stray tokens...`).
- 마디 길이 오산이 가장 흔하다. 파싱은 통과하지만 마디선은 8개인데 마디 안 박자 합이 틀린다. gpt rdefault의 5건, rnone의 대부분, haiku rnone이 그렇다. 틀리면 이후 마디가 다 밀려 총 길이(예 33/4마디, 63/8마디)도 어긋난다. gemma는 4/4에서 `l8` 7개짜리 마디(7/8)를 반복했다.
- 트랙 구조: gemma가 같은 트랙 블록을 반복 출력(Lead·Bass를 4마디씩 두 번)하거나 요청에 없는 Piano·Drums·Bass 트랙을 내는 경우 5건. 나머지 두 모델은 구조 문제가 haiku rdefault 잘림 외에 없었다.
- 드럼 라벨 오류(멜로디 트랙에 라벨, ch10에 음이름)는 100개 응답 중 0건. 가사 표기 `c8"사"`와 `"-"` 멜리스마 형식 오류도 0건. 코드펜스·설명문 시작도 0건. 반대로 `n( )` 셋잇단, `&` 타이는 100개 응답 어디에도 쓰이지 않아 이 스파이크로는 검증하지 못했다(확인 못 함).

문법 자체의 문제로 보이는 지점 (검증기를 쓰며 확인)

1. `#`가 올림표이면서 주석 시작이다(5.14 토큰 표에 둘 다 있음). 모델은 올림표로 `f#`를 자주 쓴다: 전체 100개 응답에서 `f#`·`g#`가 29회. `c# d` 같은 입력에서 `# d`가 주석인지 판정할 규칙이 명세에 없다. 검증기는 「음이름 바로 뒤에 붙은 `#`는 올림표, 그 밖은 주석」으로 임의 해석했다.
2. `n( )`의 「그 길이」가 모호하다. 「괄호 안 3음이 그 길이의 2/3씩」인데 길이가 `l`인지, 각 음 뒤 숫자인지, `)` 뒤 숫자인지 정해져 있지 않다. 5.14 예시 `n(ch ch ch) ch4`는 `)` 뒤에 숫자가 없다. 검증기는 각 음의 길이(없으면 `l`)의 2/3로 풀었고 `)` 뒤 숫자는 AMBIG 경고로 남겼다.
3. 5.14의 예시 블록이 마디 길이 검증에서 경고를 낸다. Lead의 둘째 마디 `e d c2`는 3/4, Drums의 첫 마디는 1/2, 둘째 마디는 11/16이다. S0-T5의 「마디 길이가 맞지 않으면 경고」와 「REQ 5.14 예시 블록 insta 스냅샷」이 충돌한다.
4. 「공백은 토큰 구분일 뿐」이라는 규칙이 `cde`처럼 공백 없는 음 연속을 허용하는지 불명확하다. `bd`(베이스 드럼)와 `b d`(음 두 개)도 같은 문제다. 검증기는 공백 필수로 해석했다. 이번 측정에서 모델이 `cde`를 쓴 적은 없다.
5. 마디선 `|`는 「검증에만 쓰고 틱 계산에는 안 씀」인데, 모델은 마디선 개수는 맞게 쓰고 마디 안 길이를 틀린다(pipe_ok 20/20, exact 15/20, gpt rdefault). 마디 수 일치의 정의(누적 틱 기준인가, 마디선 기준인가)와 어긋난 마디의 처리(경고 후 그대로, 쉼표 패딩/절단 보정 등)가 명세에 없다.
6. 가사와 화음·타이의 결합 위치(`[c e g]4"x"`, `c8"a"&c8`)는 명세에 없다. 이번 측정에서는 나오지 않았다.

문법 때문이 아니라 모델·설정의 문제로 보이는 지점: `d6`, `c'`, `b,`, `fis` 같은 방언 혼입은 시스템 프롬프트의 긍정 규칙만으로는 막히지 않았다(프롬프트 초안에는 `fis` 금지, 옥타브 숫자 금지 같은 부정 규칙이 없다). 이 부분은 문법 변경이 아니라 템플릿 보강과 AI-6의 자동 재요청(오류 토큰 이름을 알려 주기)으로 다룰 수 있다. 템플릿 개정 후 재측정은 호출 상한 때문에 하지 못했다(확인 못 함).

## 계획에 미치는 영향

분기: 02-spikes의 SP-5 영향과 S0-T5의 「결정 요청 후 보류」 분기. 표시: S0-T5 결정 요청 필요 (문제 1, 2, 3, 5는 필요, 4와 6은 명세 보강 수준). 결정 요청 파일은 작성하지 않았다. 제안만 적는다.

모델 판정 (파싱 성공률 90% 기준을 글자 그대로 적용)

- gpt-5.6-luna: reasoning 기본 설정에서 100%로 통과하지만 p50 9.5 s, p95 19 s, 첫 토큰 8 s라 어시스트 용도로는 쓸 수 없다. reasoning을 끈 설정은 70%로 미달.
- claude-haiku-latest: 기본 70%(잘림 제외 시 11/11), reasoning 끔 60%로 미달. 기본 설정에서는 잘림이 실패의 주원인이므로 max_tokens 설계가 먼저다.
- gemma-3-12b-it(로컬급 대체): 50%, 마디 수 일치 0%로 미달. 이 템플릿 초안으로는 로컬 기본값 후보가 못 된다. 로컬 런타임 실측은 확인 못 함.
- 따라서 현재 템플릿 초안 기준으로는 어느 모델도 「reasoning을 끈 빠른 설정」에서 90%를 넘지 못한다. 기본값에서 제외하라는 규칙을 적용하기 전에, 아래 템플릿 보강 후 재측정(S7 수동 게이트의 실험실 실행 포함)을 먼저 권고한다. 생성 모델(`~anthropic/claude-haiku-latest`)은 reasoning을 켜고 max_tokens를 4,000 이상으로 두는 안이 이번 데이터와 맞는다. 어시스트 쪽은 SP-6에서 별도로 측정했다.

S0-T5 결정 요청에 담을 제안

- `#`: 올림표는 음이름 바로 뒤의 `#`, 주석은 그 밖의 위치(또는 줄 첫머리·공백 뒤)로 명세에 못 박는다. 내보내기는 `+`만 쓴다.
- `n( )`: 길이는 각 음의 길이(없으면 `l`)로 하고 그 2/3로 정하며 `)` 뒤 숫자는 금지하거나, 반대로 `)` 뒤 숫자만 허용하는 쪽 중 하나로 확정한다.
- 5.14 예시 블록의 마디 길이를 맞추거나, 예시는 마디 길이 경고가 나는 것을 스냅샷에 그대로 담는다고 명시한다.
- 마디 수 일치와 어긋난 마디의 처리 규칙을 정한다. 이번 측정에서 모델이 가장 못 맞추는 것이 마디 안 길이 합이므로 S7의 자동 점수와 고스트 클립 처리가 이 정의에 의존한다.
- AI 응답 경로는 엄격 모드(모르는 토큰 오류 → AI-6 재요청에 오류 토큰 포함)로 둘지, 느슨 모드(경고 후 건너뜀)로 둘지 정한다. 건너뛰면 음이 사라져 마디 길이가 깨지므로 엄격 모드를 권고한다.
- 템플릿 보강(문법 변경 아님): 조표가 샤프/플랫일 때 `f+`처럼 쓰라고 조표별 임시표 목록을 변수로 제공, 「`d6` `c'` `b,` `fis`는 오류」 부정 예시, 마디마다 박수 합계를 맞추라는 지시, few-shot에 해당 조성 예시.

사람이 확인해야 할 항목

- reasoning 끔/기본 두 설정의 격차가 큰데, 앱이 생성에서 reasoning을 켤지(지연 10 s 안팎 허용 여부) 정해야 한다.
- 로컬 모델(Ollama 등)의 실제 로컬 실행 결과는 이 스파이크에 없다.
- 이번 측정의 마디 수 일치율은 템플릿 초안 1벌 기준이다. 개정 템플릿으로 재측정하면 수치가 크게 달라질 수 있다.
